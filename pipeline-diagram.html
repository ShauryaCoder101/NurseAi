Detailed Pipeline Diagram

Audio-to-Prescription
Data Pipeline

End-to-end journey of a patient interaction — from voice recording at the bedside to a grounded, verified prescription stored as longitudinal patient data.

Phase 1 — Data Capture & Privacy
🎙️
Step 1 — Field
Nurse Records Patient Interview
At the rural health sub-centre, the nurse opens the NurseAI mobile app (React Native/Expo), selects or registers a patient, and begins an audio recording of the clinical interview. The app supports multi-segment recording (dual-audio) for complex cases.
👤Patient Registration
Patient is identified by a system-generated Patient ID (e.g., P-29384). Name, age, gender, and vitals are entered. The nurse also captures a photo of any physical findings if needed.
🎤Audio Capture
Audio recorded as M4A/MP4 format. Supports dual-channel capture — primary interview audio + a second supplementary audio for additional context or follow-up answers.
📶Offline Resilience
If network is unavailable, audio is queued locally with automatic retry. Rate-limit-aware retry logic with exponential backoff ensures delivery even with intermittent connectivity.
🔒
Step 2 — Device & Transit
De-Identification & DPDP Compliance
Before any data leaves the device, the system enforces strict privacy controls aligned with India's Digital Personal Data Protection Act (DPDP, 2023). Patient identifiable information is encrypted and de-linked from clinical data.
🛡️ DPDP Compliance — How Patient Identity is Protected
  • Pseudonymisation: The patient is represented only by a system-generated ID (e.g., P-29384). The mapping of ID → real name is encrypted and stored separately — never transmitted alongside clinical audio.
  • Audio file naming: Files are renamed to {nurseHash}_{patientID}_{serial}_{timestamp} — no patient name appears in any filename, path, or metadata.
  • Encryption in transit: All API calls use HTTPS/TLS. Audio payloads are transmitted over encrypted channels. JWT bearer tokens authenticate every request.
  • Encryption at rest: Audio stored in Supabase Storage uses AES-256 encryption at rest. Database fields containing patient demographics are encrypted at the column level.
  • Developer blindness: Backend developers and system administrators cannot identify any patient by name or personal details. Logs, error traces, and audit records only reference the opaque Patient ID — never real names. Even database queries return encrypted name fields that require a separate decryption key held only by authorised clinical staff.
  • Purpose limitation: Audio data is processed solely for clinical decision support. No data is shared with third parties. AI API calls use only the opaque Patient ID — never patient names.
  • Data minimisation: Only clinically relevant data is captured. Temporary audio files (e.g., follow-up answer recordings) are automatically deleted from the server immediately after AI processing.
  • Right to erasure: Patient records can be purged from the system on request, cascading through audio files, transcripts, reasoning logs, and HTML records.
📤
Step 3 — Upload
Audio Upload & Server Ingestion
The encrypted audio file is uploaded to the Node.js backend (hosted on AWS Elastic Beanstalk) via a multipart POST request. The server validates the request, authenticates the nurse, and persists the audio.
🔐Authentication
JWT bearer token validated on every request. Firebase Auth provides the identity layer. Only authenticated nurses can upload audio. User UID is extracted and linked to the record.
💾Storage
Audio saved to Supabase Storage (cloud) with a local fallback. A record is created in audio_records table with file path, size, MIME type, and a foreign key to the patient ID. No patient name in storage paths.
🏷️File Renaming
Audio file is renamed to: {nurseEmail}_{patientID}_{serial}_{original}. This de-identified naming ensures traceability without exposing patient identity.
⚡Rate Control
Server-side throttling ensures sequential AI processing. Request queue with minimum 2-second intervals prevents API overload. 429 responses trigger client-side exponential backoff.
Phase 2 — AI Processing Pipeline
📚
Step 4 — Context Assembly
Longitudinal Patient History Retrieval
Before any AI call, the server fetches all previous visit records for this patient from the database. This longitudinal history becomes context that the AI uses to give continuity-aware clinical recommendations.
🗂️History Query
SQL query fetches all prior transcripts for this Patient ID, ordered chronologically — both gemini (prescriptions) and gemini-diagnosis (diagnoses) records. Each entry includes the exact timestamp and content.
📋Context Format
History is assembled as:
Visit (date, type):\n[full clinical content]
separated by --- delimiters. This becomes the LONGITUDINAL PATIENT HISTORY block injected into the AI prompt.
🔗Why This Matters
The AI sees the patient's full journey — not just today's complaint. It can identify chronic patterns, avoid contraindicated re-prescriptions, flag worsening trends, and ask relevant follow-ups based on previous visits.
🧠
Step 5 — Stage 1 AI Call
1Proforma — Structured Clinical Extraction
The raw audio (base64 encoded) + longitudinal patient history are sent directly to Gemini 3.1 Pro via the Generative AI API. The AI processes the audio natively — no separate speech-to-text step — preserving tonal nuances and reducing transcription error propagation.
📊Extraction Output
Structured extraction: Demographics (age, gender, occupation), Vitals (HR, BP, SpO2, RR, Temp), Chief Complaint (verbatim patient quote), and a Missing Data section flagging any gaps.
📋Proforma Interview Guide
Generated based on STG-Integration Protocol: HPI narrative using SOCRATES/OPQRST, expanded ROS with red flags, social/environmental factors, rural pharmacy check, and a Differential Calibration Table.
🔊 Why Direct Audio Processing?

Traditional systems: Audio → ASR/STT → Text → LLM (2 error steps). NurseAI: Audio → LLM (1 step). Gemini 3.1 Pro processes audio natively, eliminating transcription errors — critical for Bengali-accented English and code-mixed speech common in rural West Bengal. This preserves vocal cues (hesitation, pain indicators, tone) that text loses.

🔍
Step 6 — Stage 2 AI Call
2Diagnosis — Clarifying Questions & Differential Diagnosis
The extracted proforma data + audio + longitudinal history are processed by the 2Diagnosis prompt. The AI generates syndrome-based differential diagnoses ranked by local prevalence, and — critically — asks targeted clarifying questions to fill gaps in the clinical picture.
❓Clarifying Questions
3–4 high-discriminating questions designed to differentiate between competing diagnoses (e.g., Cardiac vs. Renal vs. Anemia). Each question includes a Bengali translation so the nurse can directly ask the patient in their language.
🩺Physical Exam Guidance
3–5 specific bedside maneuvers recommended (e.g., JVP assessment, pitting edema check, auscultation) with clinical reasoning for each — acting as a virtual clinical mentor for the nurse.
🔀Differential Ranking
Differentials ranked by local prevalence in West Bengal. Season-adjusted (monsoon → Malaria, Dengue, Scrub Typhus). Red flags for do-not-miss conditions trigger "Stabilize and Transfer" alerts.
📖History-Aware Questions
If longitudinal data shows related previous visits, the clarifying questions are cross-referenced with prior findings. The AI avoids re-asking what's already known and focuses on what's new or changed.
💡 How Clarifying Questions Improve Results
  • Nurse reads the AI-generated questions on screen and asks them to the patient
  • Nurse records the patient's answers as a second audio segment
  • This answer audio is uploaded and feeds into Stage 3 (Prescription)
  • The iterative loop narrows the diagnostic search space, improving prescription accuracy
  • If vitals are missing, the app prompts the nurse to enter them manually — the AI then integrates these into its assessment
🎙️
Step 7 — Answer Collection
Nurse Records Answers to Clarifying Questions
The nurse reads the AI's clarifying questions to the patient, records their verbal answers as a new audio segment, and submits it back to the server. This closes the diagnostic feedback loop.
🔄Feedback Loop
Stage 2 output (diagnosis + questions) is cached. The answer audio is uploaded via a separate endpoint. The server pairs the answer audio with the original diagnosis record using the audio_record_id foreign key.
🗑️Auto-Cleanup
The answer audio file is automatically deleted from the server immediately after AI processing (in the finally block). Only the AI-generated clinical output persists — never raw answer audio. This minimises data retention per DPDP.
💊
Step 8 — Stage 3 AI Call
3Prescription — RAG-Grounded Clinical Management Plan
The diagnosis text + answer audio + longitudinal history are combined and sent to the 3Prescription prompt. This is where the final management plan is generated — and where RAG (Retrieval-Augmented Generation) plays the critical role of grounding every recommendation in verified medical knowledge.
📖 RAG — Grounded on 30+ Healthcare Textbooks & Guidelines
  • Knowledge base: The prescription prompt is grounded on 30+ authoritative healthcare textbooks, clinical guidelines, and government protocols integrated into the AI's reasoning context.
  • Guideline hierarchy: (1) West Bengal WBHFW protocols → (2) GoI/ICMR national guidelines → (3) WHO/UpToDate global guidelines. Local guidelines always take precedence.
  • Mandatory search triggers: Red flags → search ICMR treatment guidelines. Public health disease → search WB reporting protocols. Referrals → search WB government hospital referral criteria.
  • Search-and-Extract protocol: AI must explicitly identify the source (e.g., "According to the ICMR 2024 PDF…"). Cross-checks search results against internal knowledge — defaults to 2026 search if conflict.
  • Zero-Tolerance Rule: If a search result is vague or doesn't specify dosage: "Current localised dosage guidelines were not found; consult a supervising doctor before prescribing [Medication]." — AI is forbidden from guessing.
  • Ghost Citation Prohibition: AI cannot mention any guideline (e.g., "Per WBHFW guidelines…") unless it was actively retrieved and verified in the current session. No phantom references.
  • Source Validation Footer: Every prescription includes: Guideline Used → Last Verified Date → Confidence Level (High/Medium/Low).
📋Prescription Output
Disposition (Local Mgmt / Stabilize & Transfer), Tier 1 & 2 diagnostics, medications with dosage/frequency/duration, diet & activity advice, follow-up timeline, and return precautions with Bengali descriptors.
🗣️Bengali Patient Education
Dedicated section in Bengali: Most likely diagnosis in simple terms, what the treatment is, what to expect (prognosis), and when to worry — using local symptom descriptors (e.g., "Buk-e-bhaar" for chest heaviness).
🧾XAI Reasoning Extraction
Every AI response includes a structured reasoning audit: ===REASONING_START=== → JSON with input_summary, step-by-step steps[], and output_summary → ===REASONING_END===. Stripped from patient-facing output but stored for review.
🔄Model Fallback
If Gemini 3.1 Pro fails (404), automatic fallback: gemini-3.1-pro-preview → gemini-2.5-pro → gemini-2.5-flash. Rate limits (429) trigger exponential backoff with retry.
Phase 3 — Storage, Verification & Longitudinal Record
💾
Step 9 — Persistence
Data Stored in Database & Longitudinal Record Updated
All AI outputs are persisted to the PostgreSQL database, linked to the patient's opaque ID. This data becomes the longitudinal record that future visits will reference — creating a growing, intelligent patient memory.
📝Transcripts Table
Both the diagnosis (source: gemini-diagnosis) and prescription (source: gemini) are saved as separate transcript records. Each linked to patient_id, audio_record_id, user_uid, and timestamped.
🧾AI Reasoning Log
Structured reasoning (input summary, step-by-step rationale, output summary, model used) is saved to ai_reasoning_log — one entry per AI stage (diagnosis, prescription, follow-up). Enables explainability audits.
💬Follow-up Log
All follow-up Q&A interactions are stored in followup_log with the question, previous context, and AI answer. The original prescription is never modified — follow-ups are additive.
📄Auto-Generated HTML
After every upload, prescription, and follow-up, the system auto-regenerates a comprehensive HTML patient record — combining demographics, vitals, all AI outputs, and doctor verifications into a printable report.
🔄 The Longitudinal Feedback Loop

Every record stored now becomes future context. The next time this patient visits, Step 4 (History Retrieval) will pull this visit's data alongside all prior visits. Over time, the AI builds an increasingly rich understanding of the patient — chronic conditions, medication history, treatment responses, and evolving symptoms. This is the core of NurseAI's patient memory.

👨‍⚕️
Step 10 — Human-in-the-Loop
Doctor Verification & Quality Assurance
A supervising physician accesses the server-rendered Doctor Verification Portal to review the AI's clinical output. This human-in-the-loop step ensures safety before the prescription reaches the patient.
✅Verification Workflow
Doctor reviews diagnosis + prescription + reasoning. Assigns verification status: Verified ✓, Needs Revision, or Flagged. Flagged outputs trigger mandatory re-evaluation before patient delivery.
📊Benchmarking
Outputs are benchmarked against multiple LLMs (GPT-4o, Grok-3, Claude, DeepSeek). Doctors evaluate using structured criteria: Diagnosis Accuracy, Prescription Appropriateness, Safety, and Explainability.
📱
Step 11 — Delivery
Clinical Output Delivered to Nurse & Patient
The verified prescription is displayed on the nurse's mobile app in real-time. The nurse reviews it, confirms understanding, and explains the bilingual patient education section to the patient in Bengali. The cycle completes.
💬Follow-up Capability
The nurse can ask follow-up questions via text — the AI answers using the full longitudinal context without modifying the original prescription. Each follow-up is logged for audit.
🚩Flagging System
If the nurse finds something concerning, they can flag the suggestion. Flagged records are routed to the doctor portal for expert review. The output is hidden from the patient view until resolved.
🔐 Developer Blindness Architecture
🔐 Why Even Developers Cannot Identify Patients
  • Opaque Patient ID: All database records, API calls, log entries, and error traces reference only the system-generated Patient ID (e.g., P-29384). No real names appear anywhere in the system's data layer.
  • Encrypted name fields: Patient names stored in the database are encrypted at the column level. The decryption key is held only by authorised clinical staff — backend developers, DevOps engineers, and system admins cannot decrypt them even with full database access.
  • Audio file privacy: Audio files are named with hashed identifiers. A developer downloading an audio file would hear a voice but have no way to link it to a named individual without the clinical decryption key.
  • AI API isolation: When audio is sent to Gemini/GPT/Claude/Grok APIs, only the opaque Patient ID is included in the prompt (e.g., Patient ID: P-29384). No names, addresses, or personal identifiers are transmitted to any external AI service.
  • Log sanitisation: Server logs record events like "Gemini processing for patient P-29384" — never "Gemini processing for [Real Name]". Error stack traces are scrubbed of any PII before being written.
  • Principle of least privilege: Even if a developer has SSH access to the production server, they see encrypted blobs in the database and opaque IDs in logs. The clinical identity layer is architecturally separated from the technical infrastructure.
📖 RAG Knowledge Base — 30+ Textbooks & Guidelines
  • Government of India STGs: NHM Standard Treatment Guidelines, Ministry of Health (MoHFW) clinical protocols, Anemia Mukt Bharat, RMNCH+A guidelines, National Immunization Schedule.
  • ICMR Guidelines: Indian Council of Medical Research treatment protocols for infectious diseases, NCDs, antimicrobial resistance, and regional endemic conditions.
  • West Bengal State Protocols: WBHFW (West Bengal Health & Family Welfare Department) — endemic disease protocols for Malaria, Dengue, Japanese Encephalitis, Scrub Typhus, and Visceral Leishmaniasis specific to the state.
  • WHO Clinical Guidelines: World Health Organization essential medicines list, emergency triage protocols, IMNCI (Integrated Management of Neonatal and Childhood Illness).
  • Medical Textbooks: Harrison's Principles of Internal Medicine, Davidson's Principles and Practice of Medicine, Oxford Handbook of Clinical Medicine, Park's Textbook of Preventive and Social Medicine, and 20+ additional clinical references.
  • Pharmacology References: KD Tripathi Essentials of Medical Pharmacology, BNF (British National Formulary), WHO Model Formulary — for drug interactions, contraindications, and dosing verification.
  • Local Context Sources: Birbhum district epidemiological data, seasonal disease surveillance reports, Swasthya Sathi referral network protocols, and rural health infrastructure mapping.
🛡️ Hallucination Mitigation — Summary of All Guardrails
  • RAG Grounding: 30+ textbooks and government protocols as the knowledge base — AI recommendations are evidence-anchored, not generated from training data alone.
  • Zero-Tolerance Rule: AI cannot guess dosages or treatments. If data is missing, it must explicitly defer to a supervising doctor.
  • Ghost Citation Prohibition: No guideline can be referenced unless actively retrieved and verified in the current session.
  • Source Validation Footer: Mandatory citation of guideline used, date verified, and confidence level on every output.
  • Multi-Model Consensus: NLP Merge Pipeline runs 3 independent LLMs → entity extraction → semantic deduplication → majority voting (2/3 agreement required).
  • Structured Reasoning (XAI): Step-by-step clinical logic extracted and logged — making every decision auditable and explainable.
  • Longitudinal Context: Full patient history prevents contradictory prescriptions and catches medication interactions across visits.
  • Human-in-the-Loop: Doctor verification required before clinical output is finalised. Flagging system for suspect recommendations.
  • Temporal Awareness: AI is calibrated to current date (2026) and seasonal disease peaks — preventing outdated recommendations.
